## 3. 必要概念：先认识产物，不急着认识模型名字

### 3.1 同一张图片，可以产生不同类型的数据

以下是教学示例，不是本地样本输出。

| 类型 | 示意 | 怎样产生 | 能回答什么 | 不能直接证明什么 |
|---|---|---|---|---|
| 可测属性 | 宽 640、高 480 | 解码后读取 / 计算 | 是否符合尺寸要求 | 内容有用、行为正确 |
| Embedding（向量表征） | `[0.12, -0.31, …]` | 模型把图像映射成一组数值 | 在指定特征空间中怎样比较图片 | 可逐维读出语义、自动获得事实真相 |
| Caption（文字描述） | “画面中一辆车靠近路口” | 模型生成文字，也可由人撰写 | 用自然语言表达内容 | 描述完整、没有遗漏或幻觉 |
| 比较分数 | 余弦相似度 0.91 | 对两份向量做运算 | 这两份表示在指定度量下多相似 | 91% 概率正确、业务行为一致 |
| 业务判断 | “候选 CR 可能引入变化” | 汇总视觉证据、版本关系和业务规则 | 缩小排查范围 | 已证明根因、已证明某版本安全 |

**Embedding 不是 caption 的另一种文件格式。** 可以直接从图片得到向量，不必先生成文字；文字本身也可以被编码成向量，但本阶段以图像 embedding 为主。

借用数仓经验：宽高像可解释的派生字段，embedding 像有版本依赖的特征列，相似度像比较结果表，业务结论像消费这些字段的判定逻辑。区别在于：向量维度通常不能逐列命名成“行人数量”“车辆速度”。

### 3.2 模型究竟多做了什么

```text
媒体字节 → 解码图片 → 预处理 → 模型编码 → 向量
                                             ↓
另一张图片走同样流程 → 另一向量 → 比较函数 → 分数 → 业务判断
```

- **解码**：把 JPEG / PNG 等变成可处理的像素。
- **预处理**：模型所需的缩放、裁剪、颜色及数值处理；具体操作取决于模型配置。
- **编码**：产生固定模型所定义的特征表示。通常可以使用已有模型，不要求自己训练。
- **比较**：在适用的特征空间中计算相似度或距离。

三个重要限制：

1. 两个模型即使输出维度相同，也不能默认逐维比较；应在各自空间内分别计算分数。
2. 模型 / 权重 / 预处理变了，结果可比性需要重新验证；相同模型名称不等于完整复现条件。
3. 相同图片在固定推理条件下通常应得到相同或非常接近的结果，但数值误差和随机处理需要控制；分数不是文件身份标识，精确重复不应仅靠 embedding 判断。

### 3.3 相似度：看起来像，不等于业务上相同

对非零向量，余弦相似度是：

```text
cos(u, v) = 点积(u, v) / (长度(u) × 长度(v))
```

它比较方向，范围为 [-1, 1]，越大表示方向越接近。1 不是“完全相同图片”的充分条件；零向量不能直接套用该公式，应视为需检查的异常输入。

普通欧氏距离 L2 则衡量两点间距离，越小越接近。但不要只看字段名字猜方向：本地 [度量实现](../../vlm-triage/lib/algorithms/embedding_metrics.py)的 `L2Similarity.compute` 默认先归一化，再返回 `1 - 距离 / 2`，所以这里的 `L2` 输出是**越大越相似的转换分数**，不是原始距离。

**为什么不能直接设“超过 0.9 就正确”？**

- 背景几乎不变，关键行人位置变了：整体分数可能仍很高。
- 画面亮度或视角改变：分数可能降低，但业务行为未必改变。
- 裁剪遗漏关键区域：模型没有看到证据，而不是证明那里没有问题。
- 模型关注的差异不一定等于业务关心的差异；阈值需在已标注的目标场景中验证。

本阶段不寻找“万能模型”和“通用阈值”，只建立“分数有条件、结论有边界”的意识。

## 4. 连接业务：vlm-triage 在消费什么

### 4.1 先把“定位”说清楚

[项目导览](../../vlm-triage/docs/project-orientation.md)描述的范围包含路测问题分析、仿真 Diff 与拐点定位。我们只学习其中的**视觉 CR 定位**，不把整个项目简化为一个相似度接口。

这里的 CR 是代码变更。可以把业务问题理解为：

> 同一个仿真场景在基线版本与待比较版本之间表现不同，中间有一批候选代码变更；能否利用视觉变化，缩小需要排查的候选范围？

- `base`：比较基线，不天然代表“绝对正确”。
- `feature`：另一端待比较版本；这里不是向量的某个“特征维度”。
- 候选 CR：关联版本 / 任务的代码变更。
- `scenario_id`：场景关联标识，用来避免跨场景混比。

**不是定位图片里车辆的像素坐标，也不是仅凭截图证明某个 CR 是事故根因。**

### 4.2 从业务目标读处理链路

以下顺序已对照 [定位服务](../../vlm-triage/lib/services/visual_cr_locator_service.py)的 `LocatorService.locate` 核对；属于静态代码证据，不代表运行成功。

| 步骤 / 对应方法 | 输入到输出 | 业务上为什么需要 |
|---|---|---|
| 获取任务 `get_tasks` | locator 信息 → base、候选 CR、feature 的场景任务关系 | 图像必须能追溯到具体版本，否则相似度不能帮助定位 CR |
| 选事件窗口 `cluster_event_windows` | 事件信息 → 采样时间窗口 | 聚焦值得比较的时间段，不把整个视频平均对待 |
| 抽取图像 `get_sample_images` | 视频及采样配置 → 图像与关联信息 | 从视频得到可计算的图像，并保留时间、版本与场景关系 |
| 计算视觉指标 `compute_visual_metrics` | 对齐的图片组 → 基于 embedding 的比较指标与 CV 指标 | 在同一采样位置比较各版本；当前代码不只使用 embedding |
| 生成结果 `get_result` | 指标变化及 CR 关系 → 场景级结果与可选证据 | 把“视觉发生变化”映射为可复核的候选代码变更 |

当前代码按 `scenario_id`、`window_index`、`sample_index` 分组，把 base 放首位、feature 放末位，再计算比较指标。**分组键一致只是对齐条件，不保证内容已经语义对齐**：时间偏移、采样区域和仿真差异仍可能造成干扰。

[Embedding 服务](../../vlm-triage/lib/services/embedding_service.py)中：

- `embed_images`：每个模型产生形如“图片数 × 向量维度”的输出。
- `compute_images_similarity`：将各图片与首张 base、末张 feature 分别比较。
- 输出逻辑形状为“图片数 × 模型数 × 度量数 × 2”；最后的 2 是两个参考端点，不是“正确 / 错误”两个类别。

这说明消费方需要的不只是向量，还需要**向量与哪张图、哪个版本、哪个采样位置相对应**。

### 5.2 练习 B：先用手工向量理解比较（20–30 分钟）

**目标 / 前置**：读完第 3.3 节，理解比较函数不是模型，也不是业务结论。

以下向量完全人工构造，不来自图片或模型：

```text
A = (1, 0)
B = (2, 0)
C = (0, 1)
D = (-1, 0)
```

1. 计算 A 与 B、C、D 的余弦相似度。
回答：1，0，-1

**核对**：正确。依次表示方向相同、正交、相反；这些向量均非零，余弦有定义。
2. A 与 B 的余弦为 1，能否证明它们来自同一个文件？
回答：不能，只能说二者方向一致，不能说就是同一个

**核对**：正确。余弦不衡量向量长度，方向相同不能证明文件身份相同。
3. 对真实图片的三类比较写预测：同一图片重复输入、轻微亮度变化、不同内容。只写预期与可能例外，不编具体模型分数。
回答：重复输入余弦相似度应该是1，轻微亮度变化会让相似度变小但接近1，不同内容会让相似度小于0

**修正版（助手整理）**：
- 同一图片重复输入：固定模型、预处理与确定性推理，且向量非零时，通常得到 1 或非常接近 1；随机裁剪、随机处理或数值误差可能造成差异。
- 轻微亮度变化：通常期望保持较高相似度，但取决于模型与预处理；可能几乎不变，也可能明显下降，不保证一定变小。
- 不同内容：通常期望比相同／近似内容更低，但可能仍为正数甚至较高；模型可能关注共同背景、忽略关键差异。
- **0 表示向量正交，不是通用的“相似／不相似”分界线；不同内容不保证小于 0。** 以上均为预测，不是实测。

自查：前三个余弦应为 1、0、-1。它们只是数学结果，不能证明实际模型会对某对图片给出这些数值。轻微变化通常期望接近，但是否如此取决于模型和预处理；不同内容也不能保证低分。

**验收**：算对方向关系，并能写出至少一个“直觉预期可能失败”的原因。不会点积时，只需按“对应分量相乘再相加”计算，不扩展数学课程。

### 5.3 练习 C：从视觉变化走向候选 CR（20 分钟）

**目标 / 前置**：读完第 4 节及两份必读文档，练习证据与结论分离。

虚构情景：同一场景、同一采样位置，CR-1 和 CR-2 的画面更接近 base，CR-3 起更接近 feature。这里没有给模型实测分数，也不是当前算法的测试用例。

1. 为什么可以优先复核 CR-3 附近，却不能直接宣布 CR-3 是根因？
回答：因为CR-3与base明显不同，CR-3可能是过渡状态，不是根因

**修正版（助手整理）**：CR-3 附近出现由更接近 base 转向更接近 feature 的变化，因此值得优先复核。但视觉变化与版本关系只是定位线索，尚未证明代码变更导致该现象；采样错位、仿真随机性和模型误判都可能干扰。不能确认 CR-3 是根因，也不能直接排除它。
2. 如果 CR-3 的采样时间错了一秒，或漏掉关键区域，会怎样影响判断？
回答：会直接导致判断结果无效，因为采样时间和区域是定位的关键条件

**修正版（助手整理）**：可能把不同阶段的画面误认为版本差异，或因漏掉关键区域而漏检、误定位，使结论可信度下降。是否失效取决于场景变化和关键内容是否受到影响，不能一概判定；应检查时间与区域对齐，必要时重新采样比较。
3. 你还需要哪些证据？可从时间对齐、原视频 / 事件日志、候选代码变更、重复仿真中选择，并说明用途。

**补充说明（助手整理）**：
- 时间对齐：排除比较了不同时刻或事件阶段的干扰。
- 原视频／事件日志：确认现象与事件上下文，避免只依赖抽样截图。
