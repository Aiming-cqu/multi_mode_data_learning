### 2.2 必要导读：从单步判断变成多步加工

你在 02 中回答的是“这一条样本满足尺寸条件吗”；现在多问两个问题：“与其他样本是否重复”“前一步移除了哪些数据”。

```text
输入样本清单
  → 输入有效性预检（框架外，异常单独记录）
  → 尺寸过滤（Data-Juicer）
  → 图像哈希去重（Data-Juicer）
  → 输出清单 + 逐步数量 + 异常记录
```

- **预检**：检查 ID 唯一、图像路径存在、图片可实际解码；异常记录应留下 ID 和原因，不能静默消失。这是我们要补的小实验环节，不是宣称框架默认已完成这些检查。
- **尺寸过滤**：只看当前样本是否合格。继续用 `min_width: 340`、`min_height: 1`，其余沿用默认值。
- **去重**：需要比较多个样本。第二个算子接收第一个算子的输出，不是重新读取全部原始输入。类似数仓中“先 WHERE，再按业务键去重”，但这里的键来自图像内容计算。
- **输出**：移除的是清单中的记录，不是删除原始图片。不同 ID 不意味着图片内容不同。

**去重语义校正（已核对本地源码）**：文档的“精确匹配”指计算出的图像哈希值相等。默认 `method: phash` 是感知哈希，并非文件字节摘要；不同文件也可能得到相同哈希。因此不能把输出解释成“所有图片内容绝对不同”。本轮显式使用 `consider_text: false`，文字差异不参与去重判断。按当前实现的遍历顺序，重复哈希保留先遇到的样本；实验应固定输入顺序，并核对实际保留 ID。

对单图样本，假如两个重复样本的尺寸判断也相同，交换两步可能不改变最终结果，但中间数量、算子处理量仍可能变化。感知哈希相同的图片不一定尺寸相同，**不能据此证明两步在所有数据上都可交换**。耗时受缓存和启动开销影响，小样本一次运行不能证明性能优劣。

### 2.3 卡点处理

- 不明白去重键：先设想两条不同 ID 的记录都引用同一张图；不要先学感知哈希数学。
- 不明白顺序：把第一步保留的 ID 写成一个集合，第二步只能从该集合中移除记录。
- 不明白统计：先填写每步输入、输出与差集，再研究计时。
- 环境或材料不足：把具体问题交给助手补说明；不要求自行安装整套模型环境。

### 4.2 运行与质量核对

1. 预检通过后运行两步配置，保存完整日志、返回状态和最终清单。
2. 本地 [算子驱动循环](../../data-juicer/data_juicer/core/data/dj_dataset.py) 的 `process()` 会记录每个算子的 `Done in ... Left ... samples`。据此填写数量与算子耗时，不把它当作包含启动时间的端到端耗时。

4. 比较预测与实测。不同则先查尺寸、哈希、输入顺序、路径和配置，不反过来修改预测。
5. 复制配置并只交换两个算子的顺序，使用不同输出位置；固定输入与参数，再比较数量、ID 与耗时。复跑也使用独立输出位置。

每步核对 `输入数 = 输出数 + 本步移除数`，不要重复计算前一步已移除的样本。比较输出 ID 集合之外，还要核对重复组保留了谁、输出媒体是否可解码。

### 4.3 异常与复现

- 单独建立异常输入版本，增加一个不存在的图片路径，不破坏任何现有媒体。框架外预检应输出异常 ID、原因与合格清单，再让合格样本进入两步管线。
- 如果预检已经拦截异常，只能说“预检已处理”，不能声称验证了框架对坏图的行为。直接送坏图进框架属于后续可选对照，需要独立运行并记录实际报错或跳过行为。
- 固定输入顺序、输入内容与媒体摘要、代码 commit、Python / 依赖版本、完整配置和命令后复跑，比较最终 ID 集合。不仅比较行数；也不要求耗时完全一致。

| 实验 | 结果与解释 | 证据及限制 |

#### 异常路径直接进入框架

证据：[异常运行日志目录](../../data-juicer/outputs/size-filter-and-duplicate/20261002_024636_85c55c/logs/) · [运行事件](../../data-juicer/outputs/size-filter-and-duplicate/20261002_024636_85c55c/events_20261002_024636.jsonl)。日志为 gzip 压缩文件，普通日志包含步骤数量，ERROR 日志包含异常堆栈。

```text
image_deduplicator.compute_hash()
→ load_data_with_context() → load_image() → PIL.Image.open()
→ FileNotFoundError（F 的图片路径不存在）
```

| 环节 | 输入 → 输出 | 移除原因 | 实测耗时 |
|---|---|---|---|
| 去重算子（含图片读取） | 6 → 3 | F 读取失败被跳过；D、E 分别与 B、A 重复 | 0.152s |
| 尺寸过滤 | 3 → 2 | A 宽度 336，小于阈值 340 | 0.299s |
| 最终导出 | 2 条 | B、C | 未单独记录 |

其中步骤数量、耗时和 F 的错误由日志直接确认；移除 ID 的归因结合输入、规则与此前单步实验解释，不声称日志逐条列出了全部 ID。

[异常包装代码](../../data-juicer/data_juicer/ops/base_op.py#L262-L273) 在允许跳过算子错误时，捕获异常、记录 ERROR 并返回空记录。本次事件为 `job_complete`，因此是“样本失败、任务继续”，不是整个任务失败；不能推广为所有异常、所有配置都会被跳过。

数量核对：**6 = 最终保留 2 + 重复移除 2 + 尺寸过滤 1 + 异常跳过 1**。F 未成功算出哈希，不应计入重复数，也不是尺寸不合格。

### 4.5 框架外预检实测（助手执行，2026-10-02）

新增 [预检脚本](experiments/precheck.py)，不导入 Data-Juicer，也不执行去重或尺寸过滤。它逐条检查：JSON 对象、非空且唯一的 `index`、非空文本、单张本地图片路径、文件存在、Pillow 实际解码。相对图片路径以输入清单目录为基准，合格输出改为绝对路径，避免换目录后引用失效。

## 5. 观察与解释

### 5.1 助手依据实验整理的结论

- 同图不同文字的 D 在 `consider_text: false` 下仍被去重，可能损失同图的另一种描述。
- 两种顺序本次最终都留下 B、C；单步去重保留 A、B、C，说明去重本身不检查尺寸。
- ERROR 日志与任务成功状态可以同时存在。输出数量正确不代表所有输入都处理成功，必须单独统计异常。
- 手工把异常输入拆成文件，解决的是实验隔离；当时尚未实现自动分流；随后新增的预检实测见第 4.5 节。

- 两种顺序的对照不等于同一配置的复跑；文件路径存在也不等于图片一定能解码。

### 5.3 内置预检查、运行时容错与框架外预检

本地 Data-Juicer **有内置预检查**，不是必须另写脚本才能使用。需要区分三层：

| 机制 | 检查内容 | 与本实验的关系 |
|---|---|---|
| 内置 preflight | 算子名、参数名与类型；部分字段检查、执行器兼容性和导出路径检查 | 检查管线配置是否合理，不逐条打开图片 |
| 算子运行时容错 | 实际读图失败时，根据配置抛错或记录并跳过 | 本次 F 在计算哈希前读图失败，记录 ERROR 后被跳过，任务继续 |
| 框架外预检 | 本实验脚本检查 ID、路径、实际解码，输出合格与异常清单 | 为学习数据质量分流而补充，不是运行 Data-Juicer 的必需步骤 |
