## 3. 必要概念：规模化首先是测量问题

### 3.1 时间花在哪，先区分层次

这张图分三层。横向箭头是时间先后，竖向箭头是**放大看内部**，不是下一步：

```text
【第 1 层｜进程级】
程序启动与导入 → 配置解析 → 执行器初始化 ─┐
                                        │ 进入 executor.run()
【第 2 层｜run() 内部】                  ↓
加载样本清单 → 加载算子 → ┌ 算子处理 ┐ → 导出
                         └────┬────┘
                              │ 放大这一格（N 个算子重复 N 次）
【第 3 层｜单个算子内部】      ↓
              媒体读取 → 解码 → 计算 → 写回中间字段
```

读图要点：

- 第 3 层只展开第 2 层的「算子处理」这一格，与「加载样本清单」「导出」没有时间关系。
- 第 3 层随算子个数循环：跑 5 个图像算子，同一张图片可能被打开 5 次。
- 「加载样本清单」通常只读 JSONL 里的路径文本，不碰图片。这就是它很快、「算子处理」很慢的原因。

#### 每层落在哪个源码位置

| 层 | 阶段 | 源码位置 | 日志或计时口径 |
|---|---|---|---|
| 1 | 配置解析 | [process_data.py 第 19–20 行](../../data-juicer/tools/process_data.py#L19-L20) | `Loading configuration took ...` |
| 1 | 执行器初始化 | [第 22–38 行](../../data-juicer/tools/process_data.py#L22-L38) | `Initializing executor took ...` |
| 2 | 整个 run | [第 40–41 行](../../data-juicer/tools/process_data.py#L40-L41) | `Running executor took ...` |
| 2 | 加载样本清单 | [default_executor.py 第 171 行](../../data-juicer/data_juicer/core/executor/default_executor.py#L171) | `Loading dataset from dataset builder...` |
| 2 | 加载算子 | [第 178 行](../../data-juicer/data_juicer/core/executor/default_executor.py#L178) | `ops = load_ops(...)` |
| 2 | 算子处理 | [第 246–268 行](../../data-juicer/data_juicer/core/executor/default_executor.py#L246-L268) | `All OPs are done in ...s` |
| 2 | 导出 | [第 271–273 行](../../data-juicer/data_juicer/core/executor/default_executor.py#L271-L273) | 无独立计时，计入 `job_duration` |
| 2→3 | 单个算子 | [dj_dataset.py 第 300–311 行](../../data-juicer/data_juicer/core/data/dj_dataset.py#L300-L311) | `[3/5] OP [...] Done in ...s. Left ... samples` |
| 3 | 读取／解码／计算 | 各算子的 `compute_stats_single` 内部 | 无日志，需自行插桩 |

计时口径是逐层包含的，不能混用：

```text
端到端墙钟 ⊃ Running executor ⊃ job_duration ⊃ All OPs are done ⊃ 单个 OP 的 Done in
含导入启动    = run() 全部        含导出          不含加载与导出       含该算子内的读取解码
```

`All OPs are done` 与 `job_duration` 共用 [同一个 tstart](../../data-juicer/data_juicer/core/executor/default_executor.py#L246)，两者之差近似导出耗时。

**测到哪一层，才有权定位到哪一层**：只看 `All OPs are done = 120s` 只能说“处理慢”；看到某个算子 `Done in 90s` 才能定位到具体算子；要说“解码占 80%”，必须进入第 3 层自行插桩，日志不会提供。

#### 第 3 层的一个陷阱：可能整个被跳过

[图像尺寸算子](../../data-juicer/data_juicer/ops/filter/image_shape_filter.py)的 `compute_stats_single` 在[第 61–63 行](../../data-juicer/data_juicer/ops/filter/image_shape_filter.py#L61-L63)先检查宽高统计是否已存在，存在则直接返回。若输入 JSONL 已带旧的宽高字段，[第 73–75 行](../../data-juicer/data_juicer/ops/filter/image_shape_filter.py#L73-L75)的 `load_data_with_context` 根本不会执行，图片不会被打开。

此时“第二次跑变快”可能与图片 IO 无关，也不是缓存命中，而是压根没读图。做性能对照前必须确认输入里没有陈旧统计字段。

反过来，即使执行了读取，取的是 `images[key].width/height`。这一步是否触发完整像素解码取决于媒体加载实现，不能把尺寸过滤耗时直接当作完整解码耗时。

#### 四种时间口径

| 口径 | 含义 | 易误用之处 |
|---|---|---|
| 端到端墙钟时间 | 从启动命令到成功退出 | 包含导入、启动和初始化，不等于纯计算时间 |
| 执行器运行时间 | `executor.run()` 的范围 | 可能含加载、算子、导出，不能当作纯算子时间 |
| 算子时间 | 一次 `op.run` 周围的测量 | 包含该范围内的数据处理开销，未必只是用户函数 |
| 子步骤时间 | 为读取、解码、计算等分别设测量点 | 当前粗粒度日志不自动提供，需要另做仪表化 |

对重叠执行的阶段，不应简单相加耗时；Ray 等延迟执行路径也不能只测构建执行计划的时间。测量必须覆盖实际执行到结果完成的边界。

### 3.2 吞吐、加速比与正确性

#### 先定义符号

同一输入集、固定处理规则的前提下，一次运行需要记录这些量：

| 符号 | 读作 | 含义 | 单位 |
|---|---|---|---|
| `N_in` | N in | 进入管线的样本条数 | 条 |
| `N_out` | N out | 通过全部算子、最终导出的样本条数 | 条 |
| `N_filtered` | N filtered | 被过滤规则正常淘汰的条数（业务结果，不是错误） | 条 |
| `N_fail` | N fail | 读取或处理失败、既未通过也未导出的条数 | 条 |
| `T` | 时间 | **某个计时口径下**花费的时间 | 秒（s） |
| `T_1` | T 一 | `p = 1`（单进程基线）时的 `T` | 秒 |
| `T_p` | T p | 并行度为 `p` 时的 `T` | 秒 |
| `p` | — | 并行度：同时工作的进程／worker 数 | 个 |

下标只是标记条件：`T_1` 的 `1` 指单进程，`T_p` 的 `p` 指当时的并行度。四个条数满足恒等式 `N_in = N_out + N_filtered + N_fail`，跑完先对这一行账，对不上说明有样本被静默丢弃。

#### `T` 不是固定变量，必须绑定口径

这是最容易错的地方。`T` 本身没有唯一取值，它是 [第 3.1 节](#31-时间花在哪先区分层次)那几层计时中的**某一层**。同一次运行，取端到端墙钟还是取 `All OPs are done`，算出的吞吐是两个都“对”但完全不同的数字，不能混用、不能相除。

所以写吞吐时必须带上口径，例如“端到端输入吞吐 10 条/秒”，只写“吞吐 10 条/秒”是无意义的。

四个派生指标：

- **输入吞吐** `N_in / T`，单位＝条 ÷ 秒＝**条/秒**。衡量“喂进去多快”。
- **输出吞吐** `N_out / T`，单位同为条/秒。衡量“产出多快”，数值必然小于输入吞吐。
- **加速比** `T_1 / T_p`，单位＝秒 ÷ 秒＝**无量纲**。大于 1 才是变快；等于 1 说明并行毫无收益。前提是工作量、处理语义和计时口径三者都一致。
- **并行效率** `加速比 / p`，**无量纲**，理想为 1。`p` 取的是[第 3.3 节](#33-四个容易混淆的量)嵌套关系里的 **worker 层**，不是 block 数、也不是节点数；还要说明是配置里写的进程数还是实际起来的 worker 数——两者可能不等，见 [第 4.2 节](#42-进程参数在哪里生效)。

#### 示范算例（教学构造，非实测）

输入 500 条，导出 400 条，过滤 98 条，失败 2 条。单进程端到端 50 秒，2 进程端到端 30 秒：

```text
对账：500 = 400 + 98 + 2 ✓
单进程输入吞吐 = 500 / 50 = 10 条/秒
2 进程输入吞吐 = 500 / 30 ≈ 16.7 条/秒
单进程输出吞吐 = 400 / 50 = 8 条/秒
端到端加速比   = T_1 / T_2 = 50 / 30 ≈ 1.67
并行效率       = 1.67 / 2 ≈ 0.83
```

`p = 2` 却只快 1.67 倍、效率 0.83，属于正常现象，原因见 [第 3.4 节](#34-先用一个算例建立直觉)。若把 `T` 换成算子时间，以上四个数字全部要重算。

#### “条”不等于“张”，多模态特有的坑

数仓里一行就是一行，但这里一条样本可能挂 N 张图或一段视频。按“条/秒”算吞吐会掩盖真实工作量：1000 条各含 1 张图，和 1000 条各含 20 张图，条数相同而 IO 与解码量差 20 倍。

记录时除了条数，还要记图片总数、分辨率分布和媒体总字节量。这也是 [第 3.3 节](#33-四个容易混淆的量)说“按行均分不等于按工作量均分”的原因——一个超大视频能拖慢整个批次。

#### 正确性优先于速度

过滤掉更多样本不一定代表优化；漏读文件或跳过计算导致的“提速”不算性能收益（典型情况见 [第 3.1 节的跳过陷阱](#31-时间花在哪先区分层次)与 [第 3.5 节](#35-缓存与内存最容易制造假结论)）。

对照两次运行时，至少比较输出样本 ID、关键统计和异常集合，不只比较行数——行数相同也可能内容不同。输出顺序变化时按稳定 ID 对齐后再比，不能直接认定内容变了。

### 3.3 四个容易混淆的量

| 概念 | 通俗理解 | 增大后可能发生什么 |
|---|---|---|
| 进程 / worker 数 | 同时工作的执行单元数量 | 吞吐提高，也可能争抢 CPU、磁盘和内存 |
| 批大小 batch size | 一次函数调用处理多少条 | 摊薄调用开销，也可能增加内存、延迟或触发 OOM |
| 分区 / block | 数据拆成多少份及每份大小 | 影响任务粒度、负载和传输；不等于同时运行数量 |
| 节点数 | 有多少台机器参与 | 增加资源，也增加网络、路径一致性和部署成本 |

#### 四者是嵌套关系，不是并列选项

```text
节点（机器）   ← 有几台机器
  └─ worker   ← 每台起若干个进程／actor，受 CPU、内存、GPU 配额约束
      └─ 任务  ← worker 领到的工作单元，通常对应一个 block 或其分片
          └─ batch ← 任务内部一次函数调用喂进去的条数
```

**worker 不等于机器**。单机 `default` 执行器下 `np=4` 会起 4 个进程：一台笔记本、4 个 worker。数仓对照是 Spark——一台机器可以起多个 executor，节点≈机器，worker≈executor，任务≈task，batch≈UDF 一次处理的行数。类比只帮助理解，不意味着框架实现相同。

`block` 与 `batch` 也相互独立：block 是**数据怎么切**，batch 是**每次喂多少**。先切 block，再在 block 内部按 batch 调用函数，是两层嵌套。

#### 一个完整画面

10000 条样本、2 台机器：

```text
block：切成 20 堆，每堆 500 条          ← 数据怎么分
节点：2 台机器
worker：每台起 4 个，共 8 个            ← 有多少执行单元（≠ 机器数）
并发：8 个任务同时跑，剩 12 个排队      ← block 数 20 > 并发 8
batch：每任务内 batch_size=50
      → 500 条分 10 次调用函数          ← 每次喂多少
```

四个数字各管一层，可分别调整。切成 20 个 block 不代表 20 个在并行跑——这就是上表「分区不等于同时运行数量」。

在 Ray 路径中，block 数与并发数是两个独立旋钮：`override_num_blocks` 控制读取切分（[ray_dataset.py 第 524 行](../../data-juicer/data_juicer/core/data/ray_dataset.py#L524)，另见[第 152 行注释](../../data-juicer/data_juicer/core/executor/ray_executor.py#L152)：Ray 加载不读 `num_proc`），`TaskPoolStrategy(size=op.num_proc)` 或 [ActorPool 策略](../../data-juicer/data_juicer/core/data/ray_dataset.py#L23-L30)控制并发。`map_batches` 里的 `num_cpus`、`num_gpus` 是[每个任务申请的资源量](../../data-juicer/data_juicer/core/data/ray_dataset.py#L267-L269)，不是机器编号。

单机 `default` 路径基本不暴露 block 概念，主要靠 `num_proc`。block 是上了 Ray 才需要显式调的参数，是否值得上 Ray 见 [第 4.3 节](#43-何时才考虑-ray)，本节不要求部署。

**并行数不是越大越好**：如果单条工作极小，进程启动、序列化和汇总可能比计算本身更贵；如果磁盘已饱和，更多 worker 可能只是排队。一个超大视频还可能拖慢整个任务，按行均分不等于按工作量均分。

### 3.4 先用一个算例建立直觉

假设串行用时 100 秒，其中 30 秒无法并行，70 秒能理想均分到 4 个 worker：

```text
理想时间 = 30 + 70 / 4 = 47.5 秒
理想加速比 = 100 / 47.5 ≈ 2.11
```

即使忽略通信开销，也不是 4 倍。真实开销通常会压低收益；这个简化模型不是对实际管线的预测。

### 3.5 缓存与内存：最容易制造假结论

- 首次运行与重复运行分开记录。固定缓存策略，不把缓存命中与增加进程的收益混在一起。
- `use_cache: false` 针对框架数据缓存，不等于关闭操作系统文件缓存、媒体缓存或模型缓存。
- 相同媒体路径重复一万次不等于一万张独立图片；可做调度开销实验，不能据此推断真实读取吞吐或多样性。
- 多进程可能复制模型和工作内存；RSS 不能只看主进程，也不要把共享页简单相加当精确总内存。
- 图片解码后的内存可能远大于压缩文件。例如 4000×3000、3 通道、每通道 1 字节，仅像素约 36 MB；浮点化、批处理及中间拷贝还会增加占用。

### 3.6 重试与恢复不等于正确交付

Task 可理解为一次工作调用；Actor 可理解为长期存活、可保存状态的工作实例，适合复用初始化成本，但占用资源也更持久。它们不是“单机”和“多机”的同义词。

检查点保存中间结果，减少失败后的重算；重试仍可能造成外部写入重复。示意设计是以“样本 ID＋处理版本”标识结果，先写临时产物，确认完整后发布，并区分可重试错误与坏样本。**这是设计原则，不是本地框架已保证 exactly-once 的声明。**

## 4. 对照本地源码：只追执行相关的最小路径

### 4.1 默认执行器的计时边界

分层图、源码行号与计时包含关系见 [第 3.1 节](#31-时间花在哪先区分层次)，不在此重复。这里只补读源码时容易忽略的两点：

[运行入口](../../data-juicer/tools/process_data.py)的 `main` 用 `timing_context` 分别包住配置加载、执行器初始化与运行三项。但**模块导入发生在 `main` 之前**，未包进任何一项，因此三项之和不必等于外部墙钟时间；`from data_juicer.core import ...` 还写在[初始化分支内部](../../data-juicer/tools/process_data.py#L22-L38)，属于延迟导入，其成本被计入“初始化”而非“导入”。

[默认执行器](../../data-juicer/data_juicer/core/executor/default_executor.py)的 `run` 中，`All OPs are done` 覆盖的不只是算子计算，还包括[相邻的 DAG 监控与 tracer 逻辑](../../data-juicer/data_juicer/core/executor/default_executor.py#L246-L268)。开启 `open_tracer` 或 `pipeline_dag` 时，这个数字会包含监控自身的开销，不能直接当作纯算子时间做前后对照。

[数据集驱动循环](../../data-juicer/data_juicer/core/data/dj_dataset.py)的 `process` 中，每个 `op.run` 周围记录 `Done in ... Left ... samples`。先用这个日志定位到算子，再决定是否细分读取、解码和计算；不能凭总日志直接说“解码占 80%”。

### 4.2 进程参数在哪里生效

[算子基类](../../data-juicer/data_juicer/ops/base_op.py)的 `Filter.run` 主干：

```text
dataset.map(compute_stats, num_proc=runtime_np(), batch_size=...)
    → 可选统计导出
    → dataset.filter(process, num_proc=runtime_np(), batch_size=...)
```

统计计算与保留判断是两次处理，不是“开两个进程分别做两步”。`OP.runtime_np` 会根据自动并行和资源设置决定数量；全局 `np`、算子 `num_proc` 和最终有效并行度不能默认划等号。比较时需记录配置、日志与实际执行条件。

[尺寸算子](../../data-juicer/data_juicer/ops/filter/image_shape_filter.py)的 `compute_stats_single` 会先检查宽高统计是否已存在，存在便直接返回，读取与解码整段被跳过。该陷阱及其对性能对照的影响见 [第 3.1 节](#31-时间花在哪先区分层次)「第 3 层的一个陷阱」。

### 4.3 何时才考虑 Ray

[Ray 数据集](../../data-juicer/data_juicer/core/data/ray_dataset.py)的 Mapper 路径使用 `map_batches`，分别通过 TaskPool 或 ActorPool 处理，传入批大小及 CPU/GPU 资源参数。本地代码存在这些分支，不代表当前环境已经安装、启动或验证 Ray。

满足以下情况才值得深入：单机资源确实不足、任务能合理拆分、有足够工作量摊薄分布式开销，且数据在执行节点上可访问。笔记本上的绝对媒体路径不会因为切换执行器自动出现在其他节点。

不要直接把 [04 两步配置](../04-小型数据管线/experiments/config-shape-dedup.yaml)的 `executor_type` 改成 `ray` 就认为迁移完成。其实际顺序为去重 → 尺寸过滤；本地通用 `Deduplicator` 声明仅支持 `default`，Ray 去重有专门实现。迁移要重新核对算子支持、数据路径、全局去重语义和输出，而不是只改引擎名称。

## 6. 06B 实测路线：设计先确定，实验材料下一步准备

建议实验依次进行：

1. **功能基线**：先用小样本、单个尺寸算子确认环境和结果，排除去重改变工作量的干扰。不得宣称这是完整图像解码基准。
2. **受控规模对照**：准备有权使用、非敏感、能区分媒体多样性与重复引用的样本；至少两档规模。规模从安全的小档递增，记录图片数量、分辨率和总字节量，不以重复清单冒充独立媒体。

4. **定位与解释**：先看端到端与单算子耗时，结合 CPU、内存与 I/O 观察。若证据仍不能分出读取/解码/计算，由助手补测量点，明确额外测量开销。
5. **取舍**：只根据测量提出一项后续改动，或保留单进程。没有 GPU、Ray 或显著加速不算失败；没有测量却宣称解决瓶颈才是不成立。

运行约束：预先约定数据量、磁盘与单次时长上限；内存压力、频繁交换或异常时停止扩量。坏样本单独记录，不无限重试；不下载未知业务数据、不连接生产集群、不清空共享缓存。对照前必须确认配置不会覆盖旧输出。
