## 二、先建立宏观概念：你正在学哪一层

### 1. 多模态数据生产全流程

下面是学习用的通用示意，不是声称某个项目默认包含全部步骤。

```text
来源与使用权限
    ↓
采集 / 接收：图像、视频、文本及元数据
    ↓
组织：样本 ID、媒体路径、文本、来源等如何关联
    ↓
有效性检查：文件能否读取，必要字段是否齐全
    ↓
加工：抽帧、转换、过滤、去重等
    ↓
可选的模型加工：提取向量、打分、生成描述等
    ↓
质量核对：数量、分布、异常、抽样检查
    ↓
交付：媒体文件 + 样本清单 + 处理配置 / 版本 + 质量报告
    ↓
消费：训练、评测、检索或业务分析
```

不是每条流程都需要模型，也不是每份输出都用于训练。开始一个实验前，先说清楚消费者需要什么数据。

### 2. 对照数仓经验理解

| 多模态概念 | 可以借用的数仓理解 | 需要补的新认识 |
|---|---|---|
| 样本清单与元数据 | 表里的记录 | 一条记录可能关联一个或多个外部媒体文件 |
| 媒体读取、解码 | 读取源数据 | 文件存在不等于能正常解码，成本也不只取决于行数 |
| 加工算子 | 转换、过滤、去重步骤 | 有些步骤处理像素，有些调用模型，资源需求不同 |
| 流程配置 | 作业定义 | 规定步骤、参数和输入输出；具体能力以本地版本为准 |
| 执行器 | 驱动作业运行的部分 | 把配置中的步骤落实到数据处理，而不是自己定义质量标准 |
| Embedding | 新生成的特征字段 | 是数值向量，不是图片描述；相似度也不等于业务正确性 |
| 数据交付 | 结果表与分区交付 | 还需保证媒体引用有效，并保留处理版本与来源 |

### 3. 区分“业务流程”和“框架流程”

**业务流程回答：数据为什么这样处理？**

```text
原始图像 → 按尺寸过滤 → 合格图像清单 → 供后续使用
```

**框架流程回答：代码怎样把这件事执行出来？**

```text
运行入口
  → 读取配置
  → 准备输入数据
  → 按配置创建处理步骤
  → 执行步骤
  → 导出结果 / 记录运行信息
```

这只是待验证的阅读地图。真实调用顺序、类名、文件路径，要在你拉下来的 Data-Juicer 版本中逐一确认。

## 三、框架理解应该放在哪个阶段

**不是等最后才看，也不是一开始就通读：分三层理解。**

| 层次 | 什么时候 | 要理解到什么程度 | 暂时不看 |
|---|---|---|---|
| 第一层：整体地图 | 第一次动手前，约 1 小时 | 输入、配置、算子、执行、输出各负责什么 | 继承体系、调度、全部目录 |
| 第二层：最小调用链 | 跑通并修改一个算子后 | 自己的配置如何使一个算子处理一条样本并输出结果 | 无关算子、所有后端、复杂优化 |
| 第三层：执行机制 | 完成多步骤小作品后 | 中间数据如何传递，错误如何处理，哪些机制影响成本与复现 | 尚无实际需求的分布式内部实现 |

每次读源码，都带着一个可验证的问题。例如：“我改了宽度阈值，哪个函数会读取它？”不要用“今天看一下框架”作为任务。

### 第 2 步：跑通单一过滤实验（第 1 周后半段，3–4 小时）

**任务**：读取图片，按尺寸条件过滤，输出保留样本。

**验收**：能解释至少 3 张图片为何被保留或过滤；干净输入下，输入数减去输出数等于过滤数。

**停止条件**：先证明规则和输出一致，不追求速度。若示例不支持预想的尺寸过滤，选该版本中另一个结果可直接核对的非模型过滤步骤，并记录调整。

### 第 3 步：追一条框架调用链（第 2 周，4–6 小时）

**前置条件**：已完成第 2 步，手里有一份能运行的配置。

**行动：沿着自己的实验找答案**

1. 运行命令进入哪个入口？
2. 配置在哪里读取、校验，阈值存在哪里？
3. 算子名称怎样映射到具体实现？
4. 哪个部分驱动数据经过算子？
5. 一条样本传入算子时是什么结构？是否有先计算统计值、再判断保留的步骤？
6. 保留 / 丢弃结果怎样影响输出，最终在哪里导出？

- [ ] 每个答案记录真实文件路径、函数或类名。
- [ ] 选一条样本，通过断点或少量临时日志观察输入和输出。
- [ ] 画“入口 → 配置 → 执行器 → 算子 → 输出”的实际调用图；与预想不同就修正图。

## 五、什么时候再学分布式与框架底层

四周后，满足以下条件再进入原计划的后续阶段：

- [ ] 已有可复现的小管线，而不只是运行截图。
- [ ] 能追踪一条样本经过框架的过程。
- [ ] 知道时间主要花在读取、解码、处理还是输出；不知道时先测量。
- [ ] 能提出一个具体问题，例如“图片处理吞吐量不足，如何拆分工作并控制资源”。

这时再研究 Ray / Spark 或执行后端，学习重点是：任务怎么拆、资源怎么分配、失败怎么恢复、结果怎么保证一致。是否使用某种后端，要先确认本地工具版本能力。

**宏观框架认知放在第一天；最小源码调用链放在第 2 周；分布式机制放在小作品之后。**

## 六、每次学习怎么安排，卡住了怎么办

### 单次 60–90 分钟

1. 5 分钟：写下今天只解决的一个问题。
2. 40–60 分钟：做实验，或追一条调用链。
3. 15 分钟：记录证据、解释结果、确定下一步。

### 卡点处理

- 环境连续卡住两次学习时段：记录命令、报错和版本，单独解决环境问题，不转去补整套理论课。
- 文档和代码不一致：以实际运行路径为准，保留版本及差异记录。
- 源码连续半小时读不懂：退回一条样本和一个断点，不继续向外展开文件。
- 出现大量陌生词：只查阻碍当前实验的词，其余放入待学清单。
- 数据或服务涉及内部权限：不上传内部样本到外部模型，不将内部代码和数据放入公开作品。

### 每次记录模板

```text
日期 / 本次问题：

我的解释：

下一次唯一任务：
```
