## 概述

完善项目文档体系，让人类能快速上手、agent 能准确理解项目上下文，降低沟通返工。

## 背景

本项目工具链复杂（Pixi 多环境、pytest、pydantic-ai、mkdocs、litellm、logfire），文档覆盖面不足导致：

- **人类上手成本高**：不知道有哪些环境、哪些测试命令、文件该放哪
- **Agent 理解偏差**：instructions/rules/skills/kanban 等分类不清楚，经常误解项目约定
- **死链和错误示例**：mkdocs 中有错误链接、错误代码示例、环境名称不对等，持续误导

## 范围

**在范围内：**

- 主 README、apps/docs/tests 各 README 的引导功能完善
- 工具链说明（Pixi 环境、测试命令、格式化/类型检查）
- 安全设计文档（token 管理、local.sh 分离存储）
- instructions/rules/skills/kanban 四类 agent 文档的分类和维护
- 看板卡片模板规范化（YAML frontmatter + 结构化 section）
- mkdocs 文档错误修复（死链、错误示例、过时信息）

**不在范围内：**

- 不新增代码实现功能（纯文档层面）
- 不修改构建/CI 流程本身
- 不涉及实验报告或数据集的文档（那是各实验目录的 README 职责）

## 成功指标

| 指标 | 基线 | 目标 | 评价方法 |
| ---- | ---- | ---- | -------- |
| mkdocs 死链数量 | ~5 处已知死链 | 0 | `mkdocs build --strict` 零报错 |
| 工具链覆盖度 | 缺 pixi shebang 说明、缺环境一览（已补） | 所有核心工具在 README 中有说明 | 逐项核对工具列表 |
| Agent 分类清晰度 | rules/instructions/skills/kanban 区分未文档化 | README 中有明确分类说明 | 人类抽查验证 |
| 看板卡片模板化 | 卡片头部格式不统一、缺少成功指标/范围 | 所有 active 卡片具备 frontmatter + 成功指标 | 逐卡片审计 |
| 新人上手时间 | 未测量 | ≤ 30 分钟可跑通 `pixi run etest` | 找一位未参与项目的新人计时 |

## 验证方案

### 评价方法

- **死链**：`pixi run -e dev -- mkdocs build --strict` 零报错
- **工具链覆盖**：核对清单 — pixi(多环境/shebang)、pytest(TDD/markers)、pydantic-ai(agent 模式)、mkdocs(docs 服务)、litellm(模型路由)、logfire(可观测性)
- **卡片规范化**：逐卡片检查 frontmatter 字段完整性和 success metrics 存在性
- **上手时间**：找一位新入职/未参与项目的同事，仅凭文档完成 `git clone → pixi install → pixi run etest` 全流程

### 测试计划

- [ ] 所有 shebang 使用方式在 README 中有说明
